## User verification before commits and pushes

- Implement and test changes, then present them for the user's verification.
- Do not commit or push until the user has verified the current changes and explicitly approved committing and/or pushing them.
- Approval for an earlier change does not authorize committing or pushing subsequent changes. If more changes are made after approval, wait for renewed verification and approval.
- This rule applies to every commit and push, including documentation and agent-instruction changes.

## Branches, pull requests, and independent review

- Make all changes on a dedicated `feature/<description>` or `bug/<description>` branch, including documentation and workflow changes. Base normal work on `develop` and do not commit or push directly to `develop` or `main`. Critical production hotfix branches start from `main`.
- Increase the application version once per production release, in both `package.json` and `package-lock.json`, not once per ordinary PR. Prepare the increase on a dedicated feature branch targeting `develop` before the release PR; critical hotfixes include their own increase. Use semantic versioning for the combined changes: patch for fixes, documentation, workflow, and small visual changes; minor for backward-compatible user-facing features; major for breaking changes. Include the version in the release or hotfix PR description, and have the independent reviewer verify the increase.
- After the user verifies the changes and approves committing and pushing, push the branch and open a pull request targeting `develop`. Release PRs target `main` from `develop`; critical production hotfix PRs target `main` from a bug branch. Follow the release process in `docs/RELEASE-PROCESS.md`.
- Every PR must be reviewed by an independent agent configured to use a different model from the implementing agent. Before arranging review, inspect the current agent tools and their supported model options. Identify the implementing model from runtime metadata or explicit environment configuration, then explicitly select a different supported model when launching the reviewer. The model specified in the reviewer launch configuration is sufficient evidence when the environment does not expose the actual runtime model identifier. Record the source of the implementing model identifier and the reviewer's configured model. Do not infer model identity from branding, response style, or agent self-identification. If the implementing model is unknown or a different reviewer model cannot be explicitly selected, follow the unavailable-reviewer procedure below; do not repeatedly probe for missing metadata. A different agent name, role, or session alone does not establish a different model. Review the actual PR diff, relevant context, and validation results for correctness, regressions, and missing tests.
- Record each review using this format: reviewed PR and head commit SHA; implementing model identifier and its source; reviewing model identifier from the launch configuration; findings with severity and file references (or "No findings"); validation results and limitations; verdict (approved or changes requested). In Air, use `mcp_Air_add_comment` or its exposed equivalent when available and applicable to the current review mode. Otherwise, provide the record in chat. Before merging, ensure the record is also attached to the PR; an Air comment or chat summary alone is insufficient unless it is persisted to the PR. Verify persistence from a tool result that explicitly identifies the target PR and created comment/review URL or ID, or by reading the target PR's comments/reviews and locating the record for the reviewed head SHA. A generic success response or an Air-local comment ID is not proof of PR persistence. If persistence is unconfirmed, check the PR once when a read tool is available before attempting another write, to avoid duplicate comments. If no direct PR-persistence tool is available or persistence still cannot be confirmed, provide the complete, ready-to-paste review record in chat, report the limitation once, and request manual posting with a PR comment/review link. Leave the PR unmerged until posting is verified through PR read access or explicit user confirmation identifying the target PR, posted review link, and reviewed head SHA. Continue other authorized work; retry only when tools, access, or new evidence become available.
- Address any blocking findings and have the updated changes reviewed again. Any changes made after user approval also require renewed user verification before committing or pushing, as specified above.
- Merge ordinary PRs into `develop` only after the reviewing agent approves the current revision and all required checks pass. A successful review authorizes completing that integration merge. Merging a release or hotfix into `main` additionally requires explicit user approval to release the exact tested revision; approval to commit and push alone is not deployment approval. Any change to the candidate requires renewed validation, review, and user verification. Do not bypass the PR workflow.
- If only one model is available, model selection is unsupported, or the implementing model is unknown, report that limitation once and continue implementation, testing, and preparation for user verification. After user approval, the branch may still be pushed and a PR opened, but leave it unmerged until an independent reviewer can be explicitly configured with a different model. State what is needed to unblock review, such as access to another model or a known implementing model identifier. Do not repeatedly retry unavailable capabilities or substitute self-review for the required independent review.

## Production releases

- Maintain one production service on Render; do not create a hosted staging site or PR preview services. Validate production candidates in native Linux amd64 Docker in GitHub Actions; local Docker validation is supplementary when the local runtime is compatible.
- `main` contains approved releases; `develop` integrates the next release. Production must deploy only approved revisions from `main`.
- Plan at most one normal release per week, preferably Tuesday in Europe/Prague, after checking match schedules. Skip a release if it is not ready; do not set up an unattended weekly deployment.
- No normal production deployments Friday through Sunday (Europe/Prague). Critical hotfixes are the exception and require explicit user release approval, checks, and independent review.
- After a release or hotfix, synchronize `main` back into `develop` through a reviewed PR. Record the actually deployed commit and verify production; a merge alone does not prove deployment succeeded.
- See `docs/RELEASE-PROCESS.md` for preparation, local checks, deployment, rollback, and one-time setup.
