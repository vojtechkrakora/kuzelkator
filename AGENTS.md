## User verification before commits and pushes

- Implement and test changes, then present them for the user's verification.
- Do not commit or push until the user has verified the current changes and explicitly approved committing and/or pushing them.
- Approval for an earlier change does not authorize committing or pushing subsequent changes. If more changes are made after approval, wait for renewed verification and approval.
- This rule applies to every commit and push, including documentation and agent-instruction changes.

## Branches, pull requests, and independent review

- Make all changes on a dedicated `feature/<description>` or `bug/<description>` branch, including documentation and workflow changes. Do not commit or push directly to `main`.
- Every pull request must increase the application version in both `package.json` and `package-lock.json`. Follow semantic versioning: use a patch increase for fixes, documentation, workflow, and small visual changes; use a minor increase for backward-compatible user-facing features; use a major increase for breaking changes. Include the new version in the PR description, and have the independent reviewer verify that the version was increased appropriately.
- After the user verifies the changes and approves committing and pushing, push the branch and open a pull request targeting `main`.
- Every PR must be reviewed by an independent agent using a different model from the implementing agent. Before arranging review, inspect the current agent tools and their supported model options. Identify the implementing model from runtime metadata or explicit environment configuration, select a different supported model, and verify the reviewer's model from the launch result or runtime metadata. If runtime metadata omits model identifiers, use explicit configuration tied to the implementing session or the reviewer's launch, provided it identifies the model actually used rather than a default or requested preference. Record the source of this evidence. Do not infer model identity from branding, response style, agent self-identification, or an unconfirmed model-selection request. If either identifier remains unknown, record it as unknown and follow the unavailable-reviewer procedure below; do not repeatedly probe for missing metadata. A different agent name, role, or session alone does not establish a different model. Review the actual PR diff, relevant context, and validation results for correctness, regressions, and missing tests.
- Record each review using this format: reviewed PR and head commit SHA; implementing and reviewing model identifiers and how they were verified; findings with severity and file references (or "No findings"); validation results and limitations; verdict (approved or changes requested). In Air, use `mcp_Air_add_comment` or its exposed equivalent when available and applicable to the current review mode. Otherwise, provide the record in chat. Before merging, ensure the record is also attached to the PR; an Air comment or chat summary alone is insufficient unless it is persisted to the PR. Verify persistence from a tool result that explicitly identifies the target PR and created comment/review URL or ID, or by reading the target PR's comments/reviews and locating the record for the reviewed head SHA. A generic success response or an Air-local comment ID is not proof of PR persistence. If persistence is unconfirmed, check the PR once when a read tool is available before attempting another write, to avoid duplicate comments. If no direct PR-persistence tool is available or persistence still cannot be confirmed, provide the complete, ready-to-paste review record in chat, report the limitation once, and request manual posting with a PR comment/review link. Leave the PR unmerged until posting is verified through PR read access or explicit user confirmation identifying the target PR, posted review link, and reviewed head SHA. Continue other authorized work; retry only when tools, access, or new evidence become available.
- Address any blocking findings and have the updated changes reviewed again. Any changes made after user approval also require renewed user verification before committing or pushing, as specified above.
- Merge the PR into `main` only after the reviewing agent approves the current revision and all required checks pass. A successful review authorizes completing the merge; do not bypass the PR workflow.
- If only one model is available, model selection is unsupported, or the models actually used cannot be verified as different, report that limitation once and continue implementation, testing, and preparation for user verification. After user approval, the branch may still be pushed and a PR opened, but leave it unmerged until a verified different-model review is recorded. State what is needed to unblock review, such as access to another model or a review from a separately configured agent with model evidence. Do not repeatedly retry unavailable capabilities or substitute self-review for the required independent review.
